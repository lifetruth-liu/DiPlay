# P3 有界核心命令队列

`CoreCommandQueue` 是内部的业务线程到核心线程桥，不是公共SessionNetwork实现。
集成到现有LwipPrototype循环，不增加native或Java执行线程，也不改变生产后端选择。

默认最多128条命令、256KiB声明的保留字节；配置只能收紧。排队、执行中、已完成但
尚未被调用线程领取的结果都占预算。超时/取消的活动命令在真正结束并完成清理前
仍占预算。元数据由128条上限约束；retainedBytes须由后续类型化调用者准确申报，
本通用组件不分析lambda捕获的对象大小，也不替调用者完成复制前的内存准入。

调用方在自身线程等待；只有核心线程运行operation，单轮最多32次尝试。Ready表示
操作完成，Pending表示尚不可进行。Pending不会自行重新排队；输入、真正到期的栈
定时器、链路readiness变化或其他命令完成时才再次变为可运行。尚未处理的批次继续
运行，而全是Pending时恢复事件等待，不对空接收进行自旋。

deadline是该命令时钟中的绝对毫秒值，0为无限等待；排队前、执行前和完成时检查。
排队到期不运行operation。调用者超时或中断可先返回；操作已经在核心线程运行时，
不能强制中止或释放其资源。如果它稍后返回Ready，discard在同一核心线程执行，
适合撤销迟到的native bind/accept结果。operation和discard均必须非阻塞；discard
抛错会进入运行器失败/关闭路径。普通单命令错误回传给该调用者，不自动关闭所有命令。

已按时提交完成的结果可以在deadline过后被领取；完成先于关闭时也保留其交付结果。
关闭取消其余等待/活动调用并拒绝新命令。底层上下文后续由原核心线程关闭；没有
“调用者已超时，所以另一个线程可以free native”的例外。中断标志保留。

队列锁不跨operation、discard或唤醒回调持有。运行器signal到队列锁的访问，配合
入队后才唤醒运行器，避免相反锁顺序。核心线程不能同步调用自己的阻塞call。
现有核心循环仍交替处理32帧输入、32命令和32帧输出，等待时间取native定时器、命令
deadline及链路重试的最小值。nativeEcho工厂使用同一会话单调时钟供核心与命令使用。
Snapshot增加commandCount/commandBytes用于观察仍由桥持有的命令及声明字节。

定向测试覆盖实际pump线程、无进度不重试、排队超时、活动超时后晚到结果清理、
活动/未领取结果仍占预算、数量/字节耗尽、关闭原因、线程中断和单命令失败隔离。
运行器测试覆盖真实输入唤醒Pending及requestStop取消等待；设备测试通过命令桥在
真实native创建线程读取stats。测试中故意阻塞的operation只用于模拟晚到结果，
不代表实际命令可违反非阻塞合同。

每个端点可创建独立Scope，把其发送、接收等命令关联到该scope。cancel原子记录首个
终止原因，取消该scope下尚未提交结果的命令，并拒绝后续调用；其他scope和无scope
命令继续运行。取消无需命令槽或额外控制队列，因此满队列下也能唤醒等待者。
已提交结果仍可领取；执行中的取消命令继续占预算，迟到结果仍在核心线程discard。
scope绑定队列身份，跨队列使用被拒绝；普通scope没有注册表，资源scope仅在释放前
保留控制登记，避免长期保留已关闭端点。scope仅承载取消状态，取消本身不关闭
native端点，不提供重置或复用功能。
运行器提供newCommandScope/cancelCommands及executeCommand的scope参数，停止时
仍统一取消全部等待者。单端点取消不停止运行器，也不会设置会话failure。

新增测试覆盖同端点排队与Pending同时取消、其他端点隔离、满队列取消、首个原因、
取消后拒绝新调用、活动结果迟到清理与预算、已提交结果和跨队列身份检查。
运行器另测Pending被唤醒且其他命令继续完成；这些不证明native端点已经关闭。

`newResourceScope`为需要核心线程释放的端点预留一个资源槽。默认最多80个，配置只能
收紧，对应32 TCP、16 listen、32 UDP的总上限；这是统一上限，不替代各类型限额。
登记时保存非阻塞release，回调只能捕获有界端点标识与元数据，不可承载媒体负载。
资源槽覆盖OPEN、已排队关闭和正在释放三个阶段，直到回调返回才可再次使用。
控制队列在构造时预留容量，关闭请求不依赖128条业务命令或256KiB负载预算。
所有配置校验在容量分配之前执行；无效资源上限必须是参数错误，不能先尝试分配。

closeResource原子取消scope等待者，并将释放操作最多排队一次；调用返回只表示是否
首次排队，不是同步释放确认。核心循环优先处理关闭操作，仍与业务命令共享每轮
32次预算，因此不跳过帧输入、输出与定时器调度。已运行的业务操作不能被跨线程
打断；其迟到结果先discard，再由核心线程执行释放。普通cancel仅取消等待者，
不会自动请求资源释放；已取消scope仍能调用closeResource完成关闭。

全会话stop丢弃尚未执行的关闭回调，之后由原有核心销毁屏障释放所有native端点。
正在执行的关闭操作继续占资源槽直至返回；不从停止线程释放其对象。release抛错
不重试，异常传给运行器并触发整上下文停止，防止部分释放后重复调用。
资源表仅保留仍待释放的资源scope；释放后删除回调，不保留历史端点注册记录。
运行器增加newResourceScope/closeResourceScope及resourceScopes/closingResourceScopes
观察值。这些值表示Java控制登记，不等同于native端点存活计数；全会话停止期间，
二者可能暂时不同。回调执行时间仍依赖非阻塞实现，不以宿主测试宣称设备关闭时限。

资源队列测试覆盖预留配额、满业务队列关闭、一次释放、核心线程归属、已取消scope
继续释放、迟到结果先清理、全会话停止、释放抛错、运行中槽位保留、批次上限和
scope身份。运行器测试另测实际唤醒和释放异常后的上下文销毁。

仍需公共UDP适配、类型化拥有型缓冲的准入、完整deadline
竞态合同、TCP及会话集成。当前通用队列的字节计数不证明整个Java/native后端已经
满足全部资源预算，也不替代G2的实际NCM/ARM或G3的两后端契约验收。
