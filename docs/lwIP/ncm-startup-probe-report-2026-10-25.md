# NCM 启动暂停与 DAD：当前设备单变量对照

代码清理状态：按用户要求已删除 PROBE 开关、独立探测、额外 DAD/JNI 轮询和启动测量代码，保留原有默认连接行为。本报告及数据为清理前 APK 的历史实验记录。

## 结论

本地恢复机制确有额外耗时，但不是首次 OUT 成功前十几秒等待的主要来源。独立探测 B 将暂停调用从 A 的 82–133 次降到 1 次，仍需等待 13.652–20.315 秒才首次成功写入。不能继续把这段等待解释成“本地 DAD 一直重置，所以没有尝试 USB 写入”。

B 在本次样本的连接总耗时中位数为 20.294 秒，A 为 22.901 秒，观察到改善 2.608 秒（约11.4%）。但相邻配对有两组 B 总耗时更慢，最慢连接及最长 NCM 等待几乎没有改善，不能把全部中位数差值当作已证实的固定收益。主要长等待尚未解决，默认仍 A，B 仅为 debug 对照策略。

## 方法与实现

- 当前设备 MI 5s Plus、Android 8.0.0，已连接的 iPhone，实际后端 USERSPACE。
- 同一个 APK，唯一配置变量为 `lwipStartupPolicy`：A=`LEGACY`，B=`PROBE`。ABBA 顺序重复5组，各10次主动重连。
- 两组均默认复用完整 USB 配置，旧 active 资源释放后才启动；无10秒模式切换。兼容关闭、20ms启动写超时、2秒Start重发静默窗口、轮询和单次恢复规则相同。UI断开命令返回后固定等待1秒，不含ADB命令开销。
- A 保留原有全部暂停/恢复调用。B 保留初次排队暂停，将同一份自身 DAD NS 留在 USB 写线程，每次失败后等100ms重试，最多250次/30秒；只有首次实际写成功才恢复核心链路并重新完成DAD。每个runner最多一次独立探测。非DAD帧不重试，硬错误直接终止，取消唤醒探测等待。
- 未测试“直接删除初次排队暂停”：native把进入软件队列视为已发送，直接删掉可能在USB仍失败时提前完成DAD。B测试的是用有界独立探测取代反复恢复循环，未绕过地址验证。
- 新诊断记录直接ICMPv6头的类型/代码/DAD特征、暂停原因和调用计数、恢复调度、队列等待及native tentative/preferred变化。IPv6扩展头不冒充直接ICMPv6/TCP；不是完整抓包，不输出地址或载荷。
- native地址状态观察使用现有core getter，只读状态，不运行定时器。优先状态确认后停止额外JNI观察。日志采样有界，回调错误不能改变传输结果。
- 计时起点为controller启动，终点为session active，不代表点击到首帧。安装后首次连接及最终恢复默认的一次连接均单列，不参与比较。

## 如何解释剩余等待

1. **USB层失败真实存在。** B在核心保持一次暂停的同时持续向USB发送同一DAD探测，仍有116–166次失败写入才成功。DAD循环没有阻止这些实际调用，因此不是主要十几秒的来源。B最长仍等待20.315秒。
2. **协议栈驱动探测造成了较小的检测滞后。** A依赖约1秒节奏的新协议包，up后新一批RX出现到首次OUT成功为122–889ms；B为5–87ms。这里RX是观测到的新接收活动，不能精确等同物理OUT可写时刻，但两组差异与更密集的独立探测一致。
3. **DAD在可写后也被重新计时。** A几乎固定还需1.99秒；B为1.057–1.791秒。这个本地阶段确实更快，但2秒Start静默窗口仍在，B相应多等了一段DAD后到TCP的时间，不能将DAD提前的约0.7秒直接累加为总连接收益。
4. **up通知不是放行条件。** B收到up后仍需6.327–7.392秒才首次OUT成功。iPhone通常在Start后约0.13秒已发送SYN，说明认证/控制链路及首次连接请求已经完成。剩余长等待集中在实际OUT成功边界以前。
5. **具体USB失败原因尚未确定。** Java负返回值不能区分timeout、STALL及其他主机/设备错误。新一批IPv6接收活动与OUT恢复接近，提示应继续查iPhone NCM数据通道启用和主机USB事务；这只是定位方向，不能把iPhone内部状态或NAK写成已证实根因。

相邻两轮构成10组配对（AB或BA）。B的NCM等待7/10组更短，差值B−A范围−5.784至+2.997秒，中位数−2.373秒；总耗时8/10组更短，范围−4.976至+3.066秒，中位数−3.209秒。配对结果仍有明显波动，不能把本次整体中位数差值全部归因于已解释的本地计时收益。无多设备、物理拔线或长稳覆盖。
