# USB 有线用户态网络后端开发与测试方案

日期：2026-10-21。适用项目：DiPlay。状态：分阶段开发中，已有接口基础和公共会话宿主，尚未完成 lwIP 集成或设备验证；进度和运行证据见 [实施记录](execution-status.md)。

**目标：**在车机无法创建 Android VPN 时，使用应用内 lwIP 网络栈承载 USB NCM 上的 CarPlay IPv6 通信，无需 root、ADB 授权或系统 TUN；保留原有 VPN 和无线网络路径。

**架构：**AirPlay 通过会话级网络接口访问 TCP/UDP；现有系统 Socket 与新增 lwIP 后端实现同一契约。USB 继续使用现有 NCM 收发机制，lwIP 通过虚拟 Ethernet netif 接收和发送帧。

**技术栈：**Kotlin/JVM、Android USB Host、JNI/C、lwIP、现有 ndk-build；native 测试使用独立的宿主构建入口。

面向执行本方案的代理：按阶段使用 `superpowers:executing-plans` 逐项推进；用户明确要求并行执行时，可使用 `superpowers:subagent-driven-development`。本文描述开发任务和验收合同，不包含已经完成的软件，也不以勾选文档替代运行证据。

## 成功标准

1. 真正无法创建 VPN 的车机能通过 USB 使用全部已支持的 CarPlay 通道；不是仅绕过授权弹窗。
2. 用户态路径不调用 `VpnService.prepare()` / `establish()`，不执行 VPN appops，不创建 TUN，不修改全局路由。
3. 现有 VPN 与无线路径保持功能；后端抽取前后的回归必须有证据。
4. 在低配 32 位 ARM 车机达到约定的吞吐、延迟、CPU 和内存预算，8 小时稳定运行、100 次插拔/重连验证通过。
5. 输入不可信、USB 不稳定、业务消费缓慢时，内存和队列有上限，关闭有界，旧连接不能影响新连接。
6. 新贡献者可以仅凭仓库文档构建、运行自动测试、采集基准并提交可复现的兼容性报告。

## 范围与限制

- 本次只增加 DiPlay 自身有线会话的网络能力；不提供互联网 VPN、全车代理或通用 NAT。
- USB 权限、iPhone 信任、CarPlay USB 模式、iAP2、MFi 认证仍是连接前提；用户态网络不能修复这些层的失败。
- 不能绕过系统对 USB Host 或应用运行本身的限制，不能保证兼容所有固件。
- IPv6 为第一目标。IPv4、mDNS 等按 P0 的通道审计和抓包结果决定，不能仅凭假设删除。
- 新后端通过功能与性能门槛前不替换当前默认路径。原型不通过时停止扩展，保留测量和失败结论。

## 阶段总览

| 阶段 | 交付 | 阻塞下一阶段的门槛 |
| --- | --- | --- |
| P0 | 通道清单、协议证据、基线、选型记录 | 范围和预算明确、测试可复现 |
| P1 | 会话级接口、系统 Socket 适配、公共会话宿主 | VPN/无线回归通过、接口契约测试通过 |
| P2 | 固定版本 lwIP、宿主 harness、NCM 原型 | IPv6/NDP、双向 TCP/UDP 与性能预检通过 |
| P3 | JNI 端点、缓冲池、取消与关闭 | 契约一致、背压有效、native 检查通过 |
| P4 | 全部 AirPlay 通道接入 | 全功能有线会话、无系统 Socket 漏出 |
| P5 | 后端选择、设置、诊断 | 失败分类正确、有限回退、无需 VPN 的启动路径成立 |
| P6 | 故障、长稳、低配性能和安全加固 | 发布矩阵与资源门槛通过 |
| P7 | 实验发布、兼容性证据、维护流程 | 满足扩大发布条件后再评估默认策略 |

依赖：`P0 → P1 → P2 → P3 → P4 → P5 → P6 → P7`。宿主协议实验可在 P1 期间独立探索，但不能据此跳过 P1 回归或 P2 决策门槛。
